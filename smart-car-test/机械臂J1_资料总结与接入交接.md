## 1. 接手先看

- 用户希望给现有三轮全向小车增加机械臂；机械臂由独立 ESP32 控制，与小车 ESP32-S3 分工。目前未实现两板通信或机械臂抓取集成。
- 用户确认六个舵机型号为众灵 **ZP15D**，已用总线逐个串接，末端是一根三针线；ESP32 核心板插在带有“总线接口”的底板上。
- 厂商 J1 资料明确：**串接后的线接拓展板任意一个总线接口即可，六个总线接口完全相同。** `−/+ /S` 对应 `GND/VIN/DAT`。不应接旁边的六路 PWM 接口。[S05 p.2；S09 p.3 图]
- **总线正极是 VIN。底板输入范围 6～12V，不代表舵机可用 12V。** 配套总线舵机介绍给出 4.8～8.4V；按资料推导，两者共同供电范围为 6～8.4V，还要以实际 ZP15D 标签、底板版本及电源实测为准。PWM 的 5V/VIN 跳帽不改变图中总线的 VIN 接法。[S01 p.1；S09 pp.1–3]
- 厂商机械臂程序路线是 **MicroPython + main.py + factory 依赖目录**；不是小车的 ESP-IDF C 工程。不能把小车 ESP32-S3 镜像烧进机械臂 ESP32。
- 当前只完成过芯片/Flash 身份读取；**没有读取机械臂上的应用文件、没有确认固件版本、没有读取舵机 ID/位置、没有烧录或主动发送动作指令。**
- 本文区分“实机已证实”“厂商文档”“建议/待验证”。不要把 PDF 示例、配套资料型号或历史 COM 号当成实机当前配置。

## 3. 接线与供电

### 3.1 总线及核心板

```text
合适的独立舵机电源 → 底板电源接线柱 → VIN/GND
ESP32 核心板 → 底板串口合成电路 → DAT/S
任意总线接口 → 000 → 001 → 002 → 003 → 004 → 005
电脑 USB → ESP32 核心板（下载/调试）
```

线缆在物理上逐个串接，但各舵机共享电源和通信总线，不是六个电机电源串联分压。接口顺序以实物丝印和插头方向为准，不凭照片的左右方向接线。

- S09 p.3 的 **KPZ-ESP32 引脚分布图**标注：串口 RX/TX 经底板电路合成为单总线 DAT；六个总线接口完全一样，图中从左到右为 GND、VIN、DAT。
- S05 p.2 明确把底部 000 号舵机的 20cm 线接到任意总线口。配套线长从下向上为 20、30、20、10、10、15cm，线长不是关节尺寸。
- 核心板 USB 口朝底板电源开关这一侧，防止整块板倒插或错位。[S06 p.3；S09 p.3]
- 不必为了接这六个舵机额外购买普通 PWM 驱动板；资料所示底板已经具备总线转换电路。实物是否正是该版 KPZ-ESP32，仍需通过照片/丝印确认。

### 3.2 电源边界

| 对象 | 文档说明 | 本项目解释 |
| --- | --- | --- |
| 底板电源接线柱 | 输入 6～12V，电源额定输出能力一般 3A 以上 | 是底板范围，不能单独决定舵机供电 |
| 配套总线舵机 | 4.8～8.4V | 用户称型号 ZP15D，但 S01 未列出型号专用电气表；还需核对标签 |
| 总线接口 | GND / VIN / DAT | VIN 直接作为总线供电标注，不能给该舵机链盲接 12V |
| PWM 舵机接口 | 5V 档用板载 5V/3A，VIN 档用输入电压 | 该跳帽属于 PWM 电源，不是总线降压开关 |
| 传感器接口 | 5V/3.3V 跳帽选择电源 | 改电源不等于信号自动电平转换 |
| 核心板 USB | 编程、调试和核心板供电 | 不作为六舵机的动力电源 |

“3A 以上”是厂商通用选型说明，不是六舵机同时带载一定够用的实测结论。实际电源标签、输出电压、峰值电流能力尚未检查。断电插拔并按极性连接；初次上电支撑机械臂，出厂流程可能立即回到直立或执行开机动作。[S07 p.1；S11 pp.11–12]

## 5. 通信层次与协议

### 5.1 三个入口不能混淆

1. **核心板 USB/CH340K**：已验证可用于 esptool。厂商还用它连接 Thonny / MicroPython。尚未确认其应用会不会把 PC 发来的 ASCII 指令转到总线；不能仅凭 COM4 可打开就认定舵机在线。
2. **底板 UART2 和 DAT 总线**：舵机 ASCII 协议，默认 115200。底板处理双线串口与单线总线之间的电路连接，实际电平和发送/回读细节仍需原理图或源码。
3. **ZLink USB 转总线模块**：ESP32 版的校准章节明确要求经 ZLink 连电脑，ZLink 跳帽置 USB、ZX，再接底板任意总线口。[S07 p.1；S04 pp.3–5] 是否随套餐提供尚未知。

两块 ESP32 后续通信优先研究底板“用户接口”，但还未指定小车侧 GPIO、未接线。不能将两板 TX 输出直接并在同一信号线上，也不能把接口旁的 5V 当作 ESP32 GPIO 的逻辑电压。

### 5.2 舵机本体命令

依据 S01 pp.1–5。下列为协议示例，**本次未执行**；位置与运动命令不是建议立即运行的测试动作。

| 用途 | 例子 | 返回/说明 |
| --- | --- | --- |
| 指定 ID 查询 | `#000PID!` | 匹配时 `#000P!` |
| 读版本 | `#000PVER!` | 如 `#000PV0.97!`，版本示例不固定 |
| 读工作模式 | `#000PMOD!` | 如 `#000PMOD1!` |
| 读当前位置 | `#000PRAD!` | 如 `#000P1500!`，单位是位置控制量 |
| 读温度/电压 | `#000PRTV!` | 如 `#000T28.1V7.4!`，格式示例有差异 |
| 定时移到位置 | `#000P1500T1000!` | 000号向1500位置运动，角度模式中时间1000ms；无返回 |
| 停在当前位置 | `#000PDST!` | 文档单播返回 `#OK!` |
| 暂停 / 继续 | `#000PDPT!` / `#000PDCT!` | 与停止后不能继续的 PDST 不同 |
| 释放 / 恢复扭力 | `#000PULK!` / `#000PULR!` | 会改变保持能力；释力可能导致机械臂下落 |
| 修改 ID | `#000PID001!` | 把000改成001；仅单独接一个设备时配置 |

格式约束：ASCII 英文符号，ID 三位 `000..254`；`255` 广播；位置 P 四位 `0500..2500`；时间 T 四位 `0000..9999`。这里的 P 是舵机的位置控制量，用户无需在 GPIO 生成六路 PWM。

厂商默认 ID 为000；成品机械臂通常已配置，无需重新改 ID。多舵机挂载时不使用 `#255PID!` 做常规扫描，以免多个设备同时回包；应逐个 ID 查询。也不向整串广播改 ID、复位配置或回中动作。[S04 p.1；S01 pp.3、5]

角度模式1/2为270°正反向，3/4为180°正反向；模式5～8为连续旋转定圈/定时模式。必须先知道当前模式，不能把所有模式下的 T 都当成毫秒。理论500～2500范围不代表机械臂装配后每个关节都可达到两端。

### 5.3 控制板应用命令与动作组

依据 S09 p.4、S11 pp.5–12、S12 pp.4–6。

| 用途 | 协议示例 | 前提 |
| --- | --- | --- |
| 多关节命令 | `{#000P1500T1000!#001P0900T1000!}` | 配套解析/总线路径工作正常 |

厂商把整机称六舵机机械臂；其中005用于夹爪开合，不应直接推导为能独立控制末端完整六维位姿的六旋转轴机器人。

Zide 使用 `.ini` 工程；G0000 为偏差基准组，调 Bias 消除装配偏差。偏差大时应校正机械装配，不靠大幅软件偏移补偿。选择爪子/气泵、磁编码/普通版本对应的动作工程，下载后可打印动作验证。[S07 pp.2–4；S11 pp.3、8]

Zide 的“双击动作组”会实际下发动作；离线执行调用已存储数据；设置开机动作会在重启/上电时运行。因此 RESET 在机械臂上**不是已验证的急停**，不能套用小车 RESET 后电机归零的行为合同。

S13 按键示例的组号：前抓3～7，前放18～21，左放22～26，右放27～31；S14 使用1组蜷缩。这些只属于配套示例工程，不代表当前板中已存在相同动作。`z_main.group_ok == 1` 是示例内部动作空闲/完成判断，不是已定义的两板通信反馈协议。

## 7. 程序组织、恢复与备份

厂商程序结构：

```text
MicroPython 固件
├─ main.py                  # 设备启动入口
└─ factory/                 # 配套模块，必须一起上传
   ├─ z_main.py             # 初始化、命令解析、动作组调度等
   ├─ z_sensor.py           # 扩展传感器逻辑（教程命名）
   └─ UART/LED/蜂鸣器等类   # 具体文件名待拿到源码核对
```

文档截图提及源码包 `J1-ESP32出厂程序-240408.zip`，位置在配套资料“003-源码例程/02-出厂程序源码”。当前检查 Downloads 顶层只看到 PDF，尚未拿到该源码包、J1固件 BIN、Zide工程/软件或底板完整电路原理图。不要把 PDF 中几张代码截图当作完整可烧录工程。

恢复方式有两种：

- **配套含boot的完整出厂镜像**：S03/S20 给出地址 `0x0`、DIO、40MHz、32Mbit（即4MB），工具示例波特率921600。只有确认镜像确为该布局的完整镜像时才适用，不能把任意 MicroPython/application BIN 都写到0。
- **MicroPython 固件 + 文件上传**：用 Thonny 选 MicroPython(ESP32)，上传完整 factory 和 main.py。已经烧过含boot出厂镜像时无需重复安装裸 MicroPython。Ctrl+C 停止解释器程序不等于停止已下发给舵机的动作；Ctrl+D 会重新执行程序。[S09 pp.5–13；S10]

实施恢复之前，应先保存当前4MB全Flash备份、校验SHA-256，并在可以读取文件时备份设备文件和动作数据。这是后续建议，本次未备份或擦写。S20 p.6 的 `read_flash 0x200000 0x100000` 只是其特定文件区示例，不能替代全板备份，不能假定该布局适用于所有固件。

## 8. 逆运动学：可利用的内容与已见问题

S14 pp.9–13 的 `ZL_KINEMATICS` 采用底座旋转 + 平面三连杆几何法，只输出 **000～003** 四个关节；004腕转、005夹爪需另行控制。文档前半介绍DH/正逆运动学，但示例并非完整通用六轴求解器。

| 参数 | 几何定义 | 示例构造值 |
| --- | --- | --- |
| L0 | 地面到001轴中心高度 | 170 |
| L1 | 001轴到002轴距离 | 105 |
| L2 | 002轴到003轴距离 | 75 |
| L3 | 003轴到闭合夹爪末端距离 | 185 |

构造函数及坐标输入内部乘10，据此应将外部输入理解为mm、内部为0.1mm；必须量实机尺寸验证。装到小车后地面参考高度和摄像头到机械臂坐标变换会变化，不能直接照抄桌面例程。

`kinematics_analysis(x,y,z,Alpha)` 求末端位置和俯仰，成功返回0，失败返回1～7；`kinematics_move(x,y,z,mytime)` 搜索俯仰并生成总线字符串。示例倾角搜索为 `range(-25,-65,-1)`，即-25到-64°。

阅读时发现以下问题，**尚未取得真实源码或运行测试确认**：

1. p.12截图已目视核对：`if self.kinematics_analysis(...): alpha_list.append(i)` 与该函数成功返回0相反，会把错误码作为真值。不能原样用于实机，应核对源码后修正为明确的成功判断。
2. `atan(x/y)` 存在象限和零点问题，`x=y=0` 的分支也不完整；移植时需正确使用与坐标约定相符的 atan2，并处理奇异点。
3. 多处除以 `sqrt(y*y+z*z)`，需处理零距离和 acos 浮点边界；不能仅保证理论可达而忽略数值错误。
4. `kinematics_move` 中 `y > 2150` 与外部坐标mm的理解不一致，可能残留内部缩放阈值；需确认。
5. 示例缺少针对实物关节碰撞、夹爪、车体和地面的完整限位/轨迹检查。P值理论范围不能代替物理安全范围。

先用已校准的有限动作完成基本抓取，再决定是否引入视觉坐标与逆运动学；这属于建议，尚未改变现有比赛任务。

## 10. 与现有小车集成的建议和待办

目前只新增知识交接，没有新增控制代码。建议保持双控制器结构：

```text
小车 ESP32-S3：摄像头/巡线/避障/任务调度
              ↓ 尚未选定并验证的通信链路
机械臂 ESP32：命令解析/动作调度/关节限位/完成与故障反馈
              ↓ 底板单总线

```

下一步可按以下顺序推进：

1. 对照底板图确认实物型号、三线插头极性、电源电压/额定电流、是否有ZLink，以及机械臂固定和初始姿态。
2. 在不会因重启动作碰撞的条件下读取/备份现有Flash与程序，拿到J1的真实源码及动作工程，确认UART2收发和USB入口行为。
3. 经已确认总线路径逐个查询000～005的ID、版本、模式、位置，记录对应实物关节；默认不改ID、模式或校准。
4. 验证停止语义后，单关节小幅、较长时间测试，记录方向、零点、限位和夹爪开合值；再验证整套有限抓取动作。
5. 确认两板链路和共享串口冲突，再定义带序号的开始/忙碌/完成/故障/停止交互；这些反馈是待开发协议，不是厂商现成承诺。
6. 小车在机械臂抓取期间先保持停车；把机械臂流程接入 `app_controller.c` 顶层仲裁。现有 `ball_approach` 的“固定踢球计时结束=完成”不能直接替代抓取完成判定。
